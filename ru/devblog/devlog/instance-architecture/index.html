С ПРЕДМЕТАМИ

Единая система объектов, владения, транзакций, репрезентаций и сохранения/загрузки состояния.

ПРОЛОГ

Для меня всегда самое сложное в написании статьи — начать. Система уже работает, в голове всё разложено по полочкам, архитектура спроектирована и реализована. Но когда открываешь пустую страницу, возникает простой вопрос: с чего начать.

Раз не получается сразу перейти к технической части, начну с эмоциональной. Так всегда проще.

Фильм «Матрица» затрагивает интересную мысль: всё, что нас окружает, можно представить как программный код. Каждая система отвечает за свою задачу, взаимодействует с другими системами и при этом может развиваться независимо от них.

Если задуматься, даже очень сложная система в своей основе может оставаться простой.

Возьмём обычный предмет из жизни — буханку хлеба.

Даже у такого простого предмета есть собственное состояние. Он может быть мокрым, грязным, горячим или холодным, повреждённым. Может лежать в рюкзаке, находиться в руках или прямо сейчас падать на землю под действием гравитации. Это состояние может меняться под влиянием внешних факторов: например, из-за дождя, ветра, падения или физического взаимодействия.

Прям как в жизни.

Это и есть состояние предмета.

Значит, в игровом мире должны существовать сам предмет, его состояние и операции, которые позволяют с ним взаимодействовать.

Предмет нужно создать, назначить ему владельца, переместить в нужное место, изменить его состояние и сохранить в базе данных. В дальнейшем с ним можно выполнять те же операции снова и снова.

Именно с этой идеи началось построение новой архитектуры взаимодействия с предметами.

ПРЕДМЕТ И ЕГО ПРЕДСТАВЛЕНИЕ

Раньше я рассматривал предмет как единое целое. Он одновременно владел данными и визуальным представлением. Но со временем стало понятно, что такой подход накладывает ограничения.

Ведь предмету необязательно постоянно находиться в игровом мире, чтобы продолжать существовать. Но он может лежать в закрытом контейнере, храниться в инвентаре или находиться на краю карты, или храниться в базе данных.

Поэтому я разделил сам предмет и его визуальное представление. Предмет хранит собственную идентичность, состояние и связи с другими предметами. Представление же отвечает за то, как предмет выглядит и взаимодействует с игровым миром.

ПРЕДМЕТ

Самостоятельная сущность

  • Собственная идентичность
  • Данные и текущее состояние
  • Связи с другими предметами
  • Не зависит от игрового мира
  • Может сохраняться и восстанавливаться
ПРЕДСТАВЛЕНИЕ

Отображение в игровом мире

  • Внешний вид предмета
  • Физическое взаимодействие
  • Взаимодействие с окружением
  • Создаётся по необходимости
  • Может быть удалено без уничтожения предмета
ОБЪЕКТ

ЯДРО СИСТЕМЫ

Центральный реестр и точка доступа ко всем Instances.

UInstanceCoreSubsystem — единственный источник истины для зарегистрированных UInstanceObject. Именно здесь находится центральная карта Instances и контролируется их жизненный цикл.

Остальные подсистемы не должны создавать собственные независимые реестры предметов. Если системе нужен Instance, она получает его через Core — по GUID или через уже имеющуюся ссылку.

REGISTER

Новый Instance получает идентификатор и регистрируется в Core.

ACCESS

Другие системы находят его через единый реестр.

UPDATE

Состояние Instance изменяется независимо от Actor representation.

UNREGISTER

При завершении жизненного цикла Instance удаляется из реестра.

Важный принцип — Instance не должен зависеть от того, загружен ли соответствующий Actor в World. Core работает с данными объекта, а не с его визуальным представлением.

ВЛАДЕНИЕ

СИСТЕМА ВЛАДЕНИЙ

Предметы могут быть частью других предметов.

В обычной инвентарной системе легко начать с массива предметов внутри персонажа. Но такая модель быстро становится ограничением, когда появляются контейнеры, экипировка, вложенные предметы и составные объекты.

В SKWOLETS отношения между Instances вынесены в отдельную UInstanceOwnershipSubsystem. Она отвечает за связи Parent / Child и позволяет строить вложенные структуры из независимых объектов.

ROOT INSTANCE Character
Inventory Container
Equipment Container
Weapon Item
Magazine Child Instance
Optic Child Instance
Suppressor Child Instance

Например, оружие может иметь собственные Instances магазина, оптики и дульного устройства. Само оружие не превращает эти объекты в свои компоненты данных: каждый из них остаётся самостоятельным Instance со своим GUID и состоянием.

Та же модель подходит для одежды, экипировки, контейнеров и транспортных средств. Разница заключается не в отдельной системе для каждого типа предмета, а в структуре Ownership и правилах конкретного объекта.

ТРАНЗАКЦИИ

СИСТЕМА ПЕРЕМЕЩЕНИЙ

Перемещение предмета — это операция над состоянием системы, а не простое изменение ссылки.

Когда Instance перемещается из одного контейнера в другой, необходимо согласованно изменить его отношения с родителями и проверить, допустима ли такая операция.

За это отвечает UInstanceTransactionSubsystem. Она отделяет операции перемещения и изменения размещения от Core и Ownership. Core хранит Instances, Ownership управляет связями, а Transaction координирует изменение этих связей как одну операцию.

01 REQUEST Запрос на перемещение Instance
→
02 VALIDATE Проверка условий операции
→
03 COMMIT Изменение Ownership
→
04 RESULT Единый результат операции

Это особенно важно для составных объектов. Например, установка магазина в оружие должна менять размещение соответствующего Instance через Transaction. Actor оружия и Actor магазина обновляются уже после успешного изменения данных.

Сначала изменяется состояние Instance-системы. Затем runtime-представления приводятся в соответствие с ним.
РЕПРЕЗЕНТАЦИЯ

ACTOR FACTORY

Actor создаётся только тогда, когда объекту действительно требуется представление в игровом мире.

UInstanceActorFactorySubsystem — единственная подсистема, которая создаёт Actor representations для Instances. Она находит подходящий Actor Class по типу Instance, создаёт Actor, связывает его с Instance и выполняет необходимую инициализацию.

Factory не должна знать, из каких частей состоит конкретный предмет. Она отвечает только за создание и регистрацию Actor. Составные объекты восстанавливают собственные дочерние представления самостоятельно.

DATA Instance GUID + Definition + State
GET OR CREATE →
WORLD Actor Bound to Instance

Например, когда создаётся Actor оружия, он связывается со своим Instance. После собственной инициализации оружие получает дочерние Instances через Ownership и запрашивает их representations у Factory. Так восстанавливаются магазин, оптика и другие установленные модули.

В результате Factory остаётся универсальной, а логика композиции находится там, где ей и место, — внутри соответствующего игрового объекта.

FACTORY CREATES ACTORS
PARENT ACTOR RESTORES CHILDREN
INSTANCE REMAINS ALIVE
ACTOR OPTIONAL
ОПРЕДЕЛЕНИЯ

DEFINITIONS И ДАННЫЕ ПРЕДМЕТОВ

Тип объекта и конкретный экземпляр — разные уровни данных.

Каждый Instance имеет собственную идентичность и состояние, но его базовые характеристики определяются Definition. Это позволяет отделить описание типа предмета от конкретного экземпляра, который существует в игровом мире.

Definitions построены на JSON. Серверный владелец может настраивать существующие предметы и определять новые варианты без необходимости создавать отдельную игровую реализацию для каждого набора параметров.

DEFINITION

Описание типа

Базовые характеристики, параметры и конфигурация конкретного вида предмета.

INSTANCE

Конкретный объект

GUID, индивидуальное состояние и отношения с другими Instances.

При этом система не ограничена одним конкретным классом предметов. Можно использовать собственные типы, наследующиеся от UInstanceObject, сохраняя единый подход к идентификации, владению и Persistence.

БАЗА ДАННЫХ

PERSISTENCE

Сохраняется Instance и его данные, а не временный Actor в World.

Persistence работает с Instance-системой. Данные объектов сериализуются в бинарный payload, а необходимая метаинформация хранится отдельно. В качестве локального хранилища используется PostgreSQL.

Такой подход позволяет сохранять не только стандартные предметы, но и пользовательские типы, наследующиеся от UInstanceObject. Для восстановления не требуется, чтобы соответствующий Actor всё время существовал в игровом мире.

RUNTIME UInstanceObject State + Ownership
SERIALIZATION ⇄
STORAGE PostgreSQL Metadata + Binary Payload

В текущей реализации используются snapshot и journal-файлы базы данных. Это часть механизма хранения и восстановления состояния, а не отдельная модель игровых объектов.

После загрузки Instance снова регистрируется в Core. Его отношения восстанавливаются через Ownership, а Actor representations создаются только там, где они нужны.

Важно, что это не жёсткая последовательность, которую каждый предмет обязан проходить целиком. Instance может существовать без Actor, перемещаться между контейнерами, сохраняться, загружаться и снова получать представление в мире.

ОТ ПРЕДМЕТА К СЛОЖНОЙ СУЩНОСТИ

Та же архитектура должна работать не только для небольших предметов, но и для сложных составных объектов.

Я не хочу строить отдельную систему хранения для оружия, другую — для экипировки, и ещё одну — для транспорта. В основе должна оставаться одна модель: независимые Instances, связанные между собой через Ownership.

COMPOSITE INSTANCE Vehicle
EngineInstance
Fuel TankInstance
WheelsChild Instances
CargoNested Instances
DoorsChild Instances
Other PartsChild Instances

Например, транспортное средство может состоять из двигателя, колёс, топливного бака, дверей и груза. У каждого компонента есть собственная идентичность и состояние. Вся структура связывается через Ownership и может обрабатываться общей системой Instances.

Это направление развития архитектуры: одна модель данных для предметов, экипировки, контейнеров и больших составных объектов — без необходимости превращать каждый сохраняемый элемент в постоянно существующий Actor.

ЗАКЛЮЧЕНИЕ

Эта архитектура стала фундаментом, на котором будут строиться остальные предметные системы SKWOLETS. Инвентарь, экипировка, контейнеры, оружие и транспорт больше не должны существовать как отдельные несвязанные решения.

Core отвечает за Instances. Ownership — за отношения. Transaction — за операции. Actor Factory — за представление в игровом мире. Persistence — за сохранение и восстановление.

Самое важное для меня — сохранить это разделение ответственности. Когда система станет сложнее, её отдельные части должны оставаться понятными, управляемыми и независимыми настолько, насколько это возможно.
