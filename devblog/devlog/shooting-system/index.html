01

SHOOTING IS MORE THAN A BULLET TRACE

In a multiplayer game, a weapon is not simply a line trace from a camera to a target.

Every shot has to exist in several places at the same time. The player needs immediate feedback, the server needs to remain authoritative, and other clients need to see the same event without introducing unnecessary network traffic.

For SKWOLETS, we wanted the shooting system to support actual projectile behaviour rather than relying on a simple instant-hit approximation.

The important part is that these stages are built around the same projectile behaviour. The client can predict what should happen while the server independently reproduces the authoritative simulation.

03

THE BULLET HAS A TRAJECTORY

Instead of instantly teleporting a projectile from one point to another, we simulate its movement through the world.

WEAPON ●
TARGET ◆

Each simulation step advances the projectile according to its current velocity. Gravity changes its vertical movement, drag reduces its speed, and wind can influence the trajectory.

This gives us a proper ballistic foundation for weapons where distance, timing, and projectile behaviour matter.

04

CLIENT PREDICTION

A network round trip should never decide whether a weapon feels responsive.

When the player fires, the client immediately starts its local prediction. The projectile appears and begins moving without waiting for the server to respond.

CLIENT FIRE IMMEDIATE
→
NETWORK SHOT SERVER
→
SERVER SIMULATE AUTHORITATIVE

Other players do not need to know every internal detail of the local prediction. They only need the resulting gameplay state and the visual representation of the shot.

05

SERVER AUTHORITY

Prediction improves responsiveness. It does not grant the client authority over the result.

The server receives the shot command and performs its own validation before allowing the projectile to participate in authoritative gameplay.

CLIENT

PREDICTION

Immediate visual feedback and local projectile simulation.

SERVER

AUTHORITY

Validates the shot and determines the actual gameplay result.

OTHER CLIENTS

REPLICATION

Receive the information required to represent the shot in the shared world.

This separation lets the game feel responsive without moving important gameplay decisions away from the server.

06

SPATIAL QUERIES

Hundreds of projectiles should not require checking every character in the world.

Before performing expensive hit detection, the shooting system uses a spatial structure to find only the hitboxes that can realistically intersect the projectile's path.

01 Projectile segment
02 Spatial query
03 Candidate hitboxes
04 Precise collision test

This broad-phase filtering becomes increasingly important as the number of active projectiles and players grows.

07

SHOOTING THROUGH TIME

A fast-moving multiplayer game has another problem: the target is not necessarily where it was when the shooter pulled the trigger.

Network latency means that the server receives a shot after some amount of time has already passed. By then, the target may have moved several meters.

TARGET NOW
← REWIND
TARGET SHOT TIME

The server can temporarily reconstruct the relevant historical hitbox state and perform the collision test against the pose that existed when the shot was fired.

Once the test is complete, the world returns to its current state.

08

THE ACTUAL HIT TEST

Projectile simulation and hit detection are separate stages.

During each simulation step, the projectile moves from its previous position to its new position. The server tests the entire segment between those points.

PREVIOUS ●
HITBOX
NEXT ●

This prevents fast projectiles from simply skipping over a small target between simulation updates.

If multiple objects are encountered along the trajectory, the system evaluates them in their order along the projectile path. World geometry can stop the projectile, while designated soft-cover materials can allow the projectile to continue.

10

BUILT FOR MANY PROJECTILES

The projectile simulation is centralized instead of creating a heavyweight gameplay component for every bullet.

Active projectiles are processed together by a dedicated world-level system. This keeps the simulation lightweight and makes it possible to handle large numbers of airborne projectiles without turning every bullet into an independent ticking actor.

CENTRAL SIMULATION
SPATIAL BROAD-PHASE

The important performance principle is not simply making the projectile simulation faster. It is avoiding unnecessary work in the first place.

11

REWIND PERFORMANCE

Lag compensation sounds expensive until the actual operation is measured.

The rewind system was benchmarked independently to understand the cost of temporarily applying a historical character pose and restoring it afterwards.

AVERAGE REWIND + RESTORE 0.651 μs
P95 0.900 μs
P99 1.100 μs
MAX 45.600 μs

These measurements cover the rewind and restoration operation itself. The complete production cost also includes spatial queries, collision traces, and hit processing.

Measuring every stage separately makes it much easier to understand where the real cost of the shooting pipeline is.

SHOOTING SHOULD FEEL SIMPLE.

The player pulls the trigger and sees a projectile fly. Underneath that simple interaction is a complete multiplayer pipeline built around prediction, deterministic simulation, spatial queries, historical hit detection, and server authority.

The goal is not to make the system visible to the player. The goal is to make it disappear.
