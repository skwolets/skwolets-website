BUILDING A
SHOOTING SYSTEM

Server-authoritative shooting with prediction, rewind and realistic projectile simulation

01

A BULLET IS MORE THAN A HIT

Shooting looks simple from the outside. Pull the trigger, send a bullet forward, check if it hits something.

In a networked multiplayer game, it becomes much more complicated. The client needs an immediate response, while the server must remain authoritative. Players have different latency, targets are constantly moving, and projectiles need to behave consistently across the network.

For SKWOLETS, the goal is not to create a traditional projectile Actor for every bullet. The goal is to build a centralized ballistic system where simulation, validation and hit registration are separate systems working together.

THE PRINCIPLE Simulate the bullet.
Validate the shot.
Rewind the target.
Let the server decide the damage.
02

ONE SYSTEM FOR EVERY BULLET

Bullets are not individual objects.

The system does not create a separate game object for every bullet flying through the world.
Instead, active projectiles are processed together as part of a centralized simulation.
Each projectile keeps only the state required for its ballistic calculation, while the simulation advances them in a single pass.
This significantly reduces the amount of per-projectile overhead and makes it possible to handle a large number of airborne projectiles without turning every bullet into an independent gameplay object.

The result is simple: the bullet is treated as simulation data, not as a full game entity.

03

REALISTIC BALLISTICS

The bullet does not simply move from A to B.

Every simulation step updates the projectile's velocity before calculating its next position.

300 M
↓ GRAVITY
← DRAG
↘ WIND

The physics are intentionally lightweight and implemented directly in native C++. At each simulation step, the projectile's velocity is calculated from its current velocity, gravity, drag and wind. That velocity is then used to calculate the projectile's new position.

In simple terms: velocity + gravity + drag + wind → new velocity → new position

The projectile does not need a heavyweight physics Actor or Movement Component just to calculate its trajectory.

01 GRAVITY

The projectile is affected by gravity throughout its flight.

02 DRAG

Air resistance gradually reduces the projectile's velocity as it travels through the air.

03 WIND

Wind velocity can influence the projectile's trajectory throughout its flight.

04 VELOCITY

The projectile's position is continuously calculated from its simulated velocity.

Ammunition is data-driven rather than hardcoded into the projectile simulation. Each ammunition type can define its own ballistic characteristics, lifetime, and visual behaviour through external configuration.

This also makes the system moddable. New ammunition types can be added by defining their parameters in the configuration instead of changing the underlying projectile simulation.

CLIENT PREDICTION

05

SERVER VALIDATION

Prediction is for responsiveness. The server remains authoritative.

Before the authoritative projectile is allowed to produce damage, the server validates the shot.

TIMESTAMP

Prevents the same shot from being processed more than once.

MUZZLE POSITION

The server reconstructs the expected world-space position.

CAMERA

The shot can be checked against the synchronized camera direction.

ANGLE

Impossible deviations from the camera can be rejected.

The movement system already sends predictive camera state to the server. This means the server has the information necessary to compare the requested shot against the player's current predicted view.

06

FINDING THE TARGETS

A bullet does not need to test every player in the world.

Before performing the actual collision query, the projectile system asks the Spatial Grid for potential hitbox candidates along the projectile segment.

PROJECTILE START → END trajectory segment
GRID QUERY
SPATIAL GRID CANDIDATES nearby hitboxes only
FILTERED
COLLISION TRACE actual intersection

The Spatial Grid is therefore used as a broad-phase candidate system. The expensive part of the process only runs against objects that can actually be near the projectile's trajectory.

07

REWIND

The server does not only need to know where the target is. It needs to know where the target was.

By the time a shot reaches the server, the target may have already moved. Rewind allows the hit test to use the target's historical state from the moment the shot was fired.

The server keeps a short history of recent target poses. When a shot is evaluated, the relevant historical state is selected and the hit test is performed against it.
A benchmark of a complete rewind-and-restore scope averaged roughly 0.65 microseconds per operation in the tested setup, with a P95 around 0.9 microseconds.

WHY REWIND? The projectile is simulated in the present.
The target is evaluated in the past.
08

SERVER OWNS THE DAMAGE

Prediction can show a bullet. It cannot decide who gets hurt.

The client-side simulation exists for responsiveness and visual feedback. The authoritative projectile exists on the server.

Only the server-side hit result is allowed to call the damage processing path.

CLIENT

Predicts the projectile and provides immediate feedback.

SERVER

Validates the shot and runs the authoritative simulation.

REWIND

Restores the target's historical state for hit registration.

DAMAGE

Applied only by the authoritative server simulation.

10

WHY BUILD IT THIS WAY?

Because every system solves a different problem.

⚡ RESPONSIVE

Client prediction makes shooting respond immediately instead of waiting for a server round trip.

🛡 AUTHORITATIVE

The server validates the shot, simulates the authoritative projectile and controls damage.

🎯 ACCURATE

Historical target poses allow hit registration to account for network latency and moving targets.

⚙ LIGHTWEIGHT

Centralized simulation, native runtime data and spatial candidate filtering avoid unnecessary per-projectile overhead.

11

CONCLUSION

A shooting system is not just a bullet moving forward.

It is the combination of prediction, networking, simulation, validation, spatial queries, historical state and authoritative hit registration.

In SKWOLETS, all of these parts are designed to work together without turning every projectile into a heavyweight gameplay Actor.

The client gets immediate feedback. The server remains in control. The projectile follows a real simulated trajectory. The Spatial Grid keeps candidate detection efficient. Rewind provides the historical target state. And the final damage decision always comes from the server.

SKWOLETS Predict locally.
Simulate consistently.
Validate on the server.

P.S. There are no 300 Projectile Actors flying around the world. Just one subsystem, one array, and a lot of math. 😄
