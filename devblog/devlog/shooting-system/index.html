DEVELOPMENT LOG / 002

BUILDING A HIGH-PERFORMANCE MULTIPLAYER SHOOTING SYSTEM

Designing server-authoritative shooting with client prediction, deterministic ballistics, lag compensation, rewind, and a lightweight projectile simulation.

01

SHOOTING IS MORE THAN A BULLET TRACE

In a multiplayer game, a shot is not simply a line trace executed on the client.

The system has to answer several different questions at the same time: what did the player intend to shoot, where was the projectile at a specific moment, where was the target at that moment, and which machine is allowed to decide whether damage actually happened?

The shooting architecture was therefore designed around a simple principle: the client predicts, but the server decides.

CLIENT

Prediction

The local player receives immediate visual feedback without waiting for a server round trip.

SERVER

Authority

The server validates the shot and is the only authority capable of applying damage.

WORLD

Simulation

Projectile motion, collision and historical hit registration are handled by the authoritative world.

02

KEEPING THE SHOT COMMAND SMALL

The network command contains only the information the server actually needs.

A shot does not transmit a complete world-space transform, arbitrary direction vector, or other redundant state. The server already knows the shooter and their current movement and camera state.

TIMESTAMP uint16
X uint16
Y uint16
Z uint16

The coordinates are local/relative values rather than full world-space coordinates. This keeps the command compact while allowing the authoritative simulation to reconstruct the relevant shot origin from known player state.

03

SERVER-SIDE VALIDATION

The client provides a shot command. It does not provide the final result.

When the server receives a shot, it validates the command against authoritative state already available on the server.

This includes checking the shot data, its timing, the shooter's state, and whether the requested shot is consistent with the server's view of the player's camera and origin.

Exact validation thresholds and rejection rules remain internal to the server implementation.

04

CLIENT PREDICTION

Waiting for the server before showing a projectile would make shooting feel unnecessarily delayed.

The local client therefore executes the same shooting path immediately when the player fires.

This predicted projectile is visual and responsive. It does not own authority over damage or the final hit result.

These are not three independent gameplay systems. The same deterministic projectile simulation is executed in different contexts: prediction, authority, and remote visualization.

05

DETERMINISTIC PROJECTILE SIMULATION

Projectiles are simulated centrally rather than as hundreds of independent movement components.

The projectile system is implemented as a world subsystem. Active projectiles are stored in a contiguous array and processed together during the simulation tick.

SUBSYSTEM

UProjectileSubsystem

One centralized simulation point for active projectiles in the world.

RUNTIME

Contiguous Data

Projectile runtime state is processed in a compact native array.

COLLISION

Segment Trace

Each simulation step tests the segment between the previous and next projectile positions.

The ballistic model accounts for gravity, drag and wind while remaining lightweight enough to run hundreds of active projectiles through a single world simulation.

SPATIAL QUERIES & REWIND

Lag compensation does not require rewinding every player in the world.

Before performing historical hit detection, the projectile segment is queried against the spatial grid. This produces a small set of possible hitbox candidates.

Only those candidates are then evaluated against historical snapshots.

This broad-phase filtering prevents the server from performing expensive historical hitbox work against unrelated players.

07

TIMESTAMP & DUPLICATE PROTECTION

The timestamp is not used by the clients for validation.

It exists primarily on the server side. The server keeps recently processed timestamps in a small ring buffer and can reject a shot that has already been processed.

SHOT 1842 RECEIVED
→
SERVER RING BUFFER
1838 1839 1840 1841 1842
→
RESULT ACCEPT ONCE

This keeps the network command compact while giving the authoritative simulation a simple mechanism for detecting duplicate shot commands.

08

HISTORICAL HIT DETECTION

Projectile simulation and target history are two different problems.

Deterministic ballistics tells the server where the projectile is now. Rewind tells the server where a target was at the relevant historical moment.

The server stores historical skeletal poses for hitbox evaluation. When a projectile needs lag compensation, the relevant target is temporarily evaluated at its historical state.

After the trace completes, the live pose is restored.

HISTORY

Snapshots

Historical component-space skeletal poses are captured during runtime.

SCOPED

Rewind

The relevant hitbox is temporarily moved to its historical state for the authoritative trace.

RESTORE

Live State

The original runtime pose is restored immediately after the scoped operation completes.

09

PERFORMANCE

The architecture is designed around predictable, measurable costs rather than one actor per projectile.

~300 Expected maximum airborne projectiles
0.651 µs Average single rewind + restore benchmark
1.1 µs P99 single rewind + restore benchmark

The rewind benchmark measures one complete scoped rewind operation, including pose application and restoration. Full production cost also includes spatial queries, collision traces and hit processing.

The important architectural property is that these operations are performed only where they are relevant, rather than across the entire player population for every projectile.

10

AUTHORITY FIRST

Prediction improves responsiveness. It does not grant the client authority.

Client

Sends the shot command and predicts the immediate visual result.

Server

Validates the command, simulates the projectile and performs authoritative hit detection.

Damage

Damage application exists exclusively on the authoritative server path.

Historical State

Rewind is performed server-side using recorded historical hitbox state.

Internal validation thresholds, rejection heuristics and implementation-specific security rules are intentionally not exposed as part of the public architecture.

11

BUILT FOR THE NETWORK, NOT JUST THE GUN

The goal was not simply to make bullets move. The goal was to build a shooting architecture that remains responsive for the player while keeping simulation, hit registration and damage under server authority.

Prediction, deterministic ballistics, spatial filtering, historical rewind and centralized projectile simulation form one system — each solving a different part of the multiplayer problem.
