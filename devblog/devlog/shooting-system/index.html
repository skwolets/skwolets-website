BUILDING A
BALLISTIC SYSTEM

Server-authoritative shooting with prediction, rewind and realistic projectile simulation

01

A BULLET IS MORE THAN A HIT

Shooting looks simple from the outside. Pull the trigger, send a bullet forward, check if it hits something.

In a networked multiplayer game, it becomes much more complicated. The client needs an immediate response, while the server must remain authoritative. Players have different latency, targets are constantly moving, and projectiles need to behave consistently across the network.

For SKWOLETS, the goal is not to create a traditional projectile Actor for every bullet. The goal is to build a centralized ballistic system where simulation, validation and hit registration are separate systems working together.

THE PRINCIPLE Simulate the bullet.
Validate the shot.
Rewind the target.
Let the server decide the damage.
02

ONE SYSTEM FOR EVERY BULLET

Bullets are not individual Actors.

The projectile simulation is handled by a Tickable World Subsystem. Every active projectile is stored in a runtime array and processed during a single simulation tick.

There is no need to create a separate Actor, Movement Component and Tick function for every bullet currently flying through the world.

WORLD Projectile Subsystem One simulation tick
BATCH
RUNTIME Projectile Array active projectiles
SIMULATION
RESULT Trajectory Start → End
SIMULATION CENTRALIZED
RUNTIME DATA ARRAY
PROJECTILE ACTORS NONE REQUIRED
ACTIVE BULLETS ~300 MAX

With a few hundred active projectiles, iterating through a native array is extremely inexpensive compared with maintaining hundreds of independent gameplay Actors.

03

REALISTIC BALLISTICS

The bullet does not simply move from A to B.

Every simulation step updates the projectile's velocity before calculating its next position.

01 GRAVITY

The projectile is affected by gravity throughout its flight.

02 DRAG

Air resistance changes the projectile's velocity over time.

03 WIND

Wind velocity affects the projectile trajectory.

04 VELOCITY

Position is calculated from the simulated projectile velocity.

VELOCITY → GRAVITY + DRAG + WIND → NEW POSITION

The physics are intentionally lightweight and implemented directly in native C++. There is no need for a full physics Actor just to calculate the trajectory of a small piece of ammunition.

04

THE SHOT DATA

The client does not send the server a complete world-space shot.

Instead, the shot command contains only the information the server actually needs to identify and validate the shot.

uint16 Timestamp

uint16 X

uint16 Y

uint16 Z

X, Y and Z represent a quantized relative position rather than a full world-space FVector. The server already knows the shooter's position and can reconstruct the world-space muzzle position itself.

The direction does not need to be trusted from the client either. The server can validate the shot against the camera state that is already synchronized through the movement prediction system.

LESS DATA The client describes the shot.
The server reconstructs and validates it.
05

CLIENT PREDICTION

Waiting for the server before showing a bullet would make shooting feel slow.

The firing client therefore runs the same projectile simulation locally as soon as the shot is created.

CLIENT Predicted Shot immediate feedback
SAME SIMULATION
SERVER Authoritative Shot damage authority
REPLICATION
OTHER CLIENTS Visual Shot replicated state

The important part is that these are not three independent gameplay bullets. They are three executions of the same deterministic projectile simulation in different contexts.

PREDICTED → SERVER → REPLICATED
06

SERVER VALIDATION

Prediction is for responsiveness. The server remains authoritative.

Before the authoritative projectile is allowed to produce damage, the server validates the shot.

TIMESTAMP

Prevents the same shot from being processed more than once.

MUZZLE POSITION

The server reconstructs the expected world-space position.

CAMERA

The shot can be checked against the synchronized camera direction.

ANGLE

Impossible deviations from the camera can be rejected.

The movement system already sends predictive camera state to the server. This means the server has the information necessary to compare the requested shot against the player's current predicted view.

[12:41:08] shot received

[12:41:08] timestamp accepted

[12:41:08] muzzle position validated

[12:41:08] camera angle validated

[12:41:08] authoritative shot accepted

07

TIMESTAMP & DUPLICATE PROTECTION

The timestamp is not used by the clients for validation.

It exists primarily on the server side. The server keeps recently processed timestamps in a small ring buffer and can reject a shot that has already been processed.

SHOT 1842 RECEIVED
→
SERVER RING BUFFER
1838 1839 1840 1841 1842
→
RESULT ACCEPT ONCE

This keeps the network command compact while giving the authoritative simulation a simple mechanism for detecting duplicate shot commands.

08

FINDING THE TARGETS

A bullet does not need to test every player in the world.

Before performing the actual collision query, the projectile system asks the Spatial Grid for potential hitbox candidates along the projectile segment.

PROJECTILE START → END trajectory segment
GRID QUERY
SPATIAL GRID CANDIDATES nearby hitboxes only
FILTERED
COLLISION TRACE actual intersection

The Spatial Grid is therefore used as a broad-phase candidate system. The expensive part of the process only runs against objects that can actually be near the projectile's trajectory.

09

REWIND

Knowing where the bullet is is only half of the problem.

The server also needs to know where the target was when the shot should have reached it.

Every rewindable character stores historical skeletal poses. These snapshots contain the component-space bone transforms and the component transform at a specific point in time.

CURRENT TARGET POSE
REWIND
HISTORICAL TARGET POSE

During server-side hit registration, the relevant hitbox proxies are temporarily moved to their historical state. The collision query is then performed against that historical pose.

WHY REWIND? The projectile is simulated in the present.
The target is evaluated in the past.
10

REWIND WITHOUT A SECOND MESH

The rewind system does not create another skeletal mesh just to represent the historical state.

The character's existing skeletal mesh is instantiated as a custom URewindableMeshComponent. It provides a controlled way to apply a historical component-space pose directly to the runtime skeletal transform buffers.

01 SNAPSHOT

Historical component-space bone transforms are stored.

02 APPLY

The historical pose is applied to the runtime transform buffer.

03 TRACE

Collision is evaluated against the historical pose.

04 RESTORE

The original pose is restored automatically.

The rewind operation is scoped using RAII. A temporary rewind object applies the historical state and restores the original state when the scope ends.

01 save current pose

02 find historical snapshot

03 apply historical pose

04 perform trace

05 restore original pose

11

LIGHTWEIGHT BY DESIGN

The system is designed around the actual workload.

There is no reason to introduce complex parallel processing for a few hundred active projectiles when a native sequential loop can process the entire batch efficiently.

ACTIVE PROJECTILES ~300
SIMULATION 1 WORLD TICK
PROJECTILE DATA NATIVE ARRAY
REWIND AVG. ~0.65 μs

A benchmark of a complete rewind-and-restore scope averaged roughly 0.65 microseconds per operation in the tested setup, with a P95 around 0.9 microseconds.

The actual production cost also depends on the number of candidates, traces and hit processing, so the important benchmark is the complete shooting pipeline rather than any single isolated operation.

12

THE BULLET DOES NOT NEED A MOVEMENT COMPONENT

Once the projectile has been simulated, collision becomes a simple question.

Where was the projectile at the beginning of the simulation step? Where is it now?

PREVIOUS LOCATION → PHYSICS → NEW LOCATION → LINE TRACE

The projectile therefore does not require a full Unreal ProjectileMovementComponent. The subsystem already knows the exact trajectory segment produced by the ballistic simulation.

A line trace over that segment provides the collision test while keeping the projectile itself as lightweight runtime data.

SIMPLE COLLISION Physics determines where the bullet goes.
The trace determines what it hits.
13

SERVER OWNS THE DAMAGE

Prediction can show a bullet. It cannot decide who gets hurt.

The client-side simulation exists for responsiveness and visual feedback. The authoritative projectile exists on the server.

Only the server-side hit result is allowed to call the damage processing path.

CLIENT

Predicts the projectile and provides immediate feedback.

SERVER

Validates the shot and runs the authoritative simulation.

REWIND

Restores the target's historical state for hit registration.

DAMAGE

Applied only by the authoritative server simulation.

WHY BUILD IT THIS WAY?

Because every system solves a different problem.

⚡

RESPONSIVE

Client prediction makes shooting respond immediately instead of waiting for a server round trip.

🛡

AUTHORITATIVE

The server validates the shot, simulates the authoritative projectile and controls damage.

🎯

ACCURATE

Historical target poses allow hit registration to account for network latency and moving targets.

⚙

LIGHTWEIGHT

Centralized simulation, native runtime data and spatial candidate filtering avoid unnecessary per-projectile overhead.

16

CONCLUSION

A shooting system is not just a bullet moving forward.

It is the combination of prediction, networking, simulation, validation, spatial queries, historical state and authoritative hit registration.

In SKWOLETS, all of these parts are designed to work together without turning every projectile into a heavyweight gameplay Actor.

The client gets immediate feedback. The server remains in control. The projectile follows a real simulated trajectory. The Spatial Grid keeps candidate detection efficient. Rewind provides the historical target state. And the final damage decision always comes from the server.

SKWOLETS Predict locally.
Simulate consistently.
Validate on the server.

P.S. There are no 300 Projectile Actors flying around the world. Just one subsystem, one array, and a lot of math. 😄
